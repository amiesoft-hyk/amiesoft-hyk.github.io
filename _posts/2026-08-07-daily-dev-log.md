세 갈래로 나뉜 하루였다. 오전에는 같은 버그를 두 사람이 각자 고쳐놓은 중복 코드를 정리했고,
오후에는 엑셀 다운로드의 시간 서식을 손봤다. 마지막으로 리포트에 찍힌 이상한 숫자를 원본 테이블까지
따라 내려가 코드 문제가 아님을 확인했다.

## 오늘 한 일

### 1. 그리드 서버 정렬 중복 수정 정리 (완료)

부서 컬럼의 서버 정렬이 먹지 않던 문제를 두 사람이 **서로 다른 층위에서 각각** 고쳐, 같은 목적의 코드가 겹쳐 있는 상태였다.

- **A안** — `loadOptions.sort`를 통째로 무시하고, 그리드 인스턴스에서 컬럼 상태를 읽어 정렬 파라미터를 직접 조립
- **B안** — 원인 지점을 수정. 컬럼 전처리에서 `calculateSortValue = dataField`를 명시해 표시값 함수가 정렬 selector로 잡히는 것을 차단

원인을 고치는 B안을 정본으로 남기고 A안을 걷어냈다. A안은 화면이 직접 지정한 `calculateSortValue`를 무시하고 항상 `dataField`만 쓰기 때문에, 표시 컬럼과 정렬 필드를 다르게 두려는 의도를 봉쇄한다. `dataField` 없는 계산 컬럼은 정렬이 통째로 사라지기도 한다.

부수적으로 화면 여섯 곳에 흩어져 있던 부서 3컬럼(`센터`/`팀`/`섹션`)의 `calculateSortValue` 하드코딩도 제거했다. 공통 전처리가 동일한 값을 자동으로 넣어주므로 중복이었다. 반면 lookup 코드 컬럼과 다중헤더 계산 컬럼의 지정은 공통 조건에 걸리지 않아 그대로 뒀다.

### 2. 엑셀 다운로드 시간 컬럼 표시형식 수정 (완료)

내려받은 엑셀에서 시간 컬럼이 표시형식 '일반'의 텍스트로 저장돼 `SUM()`이 동작하지 않던 문제.

- 초 단위로 환산해 86400으로 나눈 **숫자 시간값**으로 저장하고 `numFmt`를 지정하도록 수정
- 시스템 시간 서식 대신 사용자 지정 서식 `[h]:mm:ss`를 적용했다. 대괄호가 없으면 24시간에서 순환해 `24:00:00`이 `00:00:00`으로 보인다
- 별도로 만들어뒀던 유틸 파일을 없애고 기존 엑셀 공통 유틸로 통합. 사용처 네 곳의 import 경로를 함께 정리했다
- XLSX 왕복 테스트로 서식이 파일에 실제로 보존되는지 확인 (16개 통과)

### 3. 이상 집계 데이터 원인 추적 (이관)

리포트의 시간 합계가 `24:00:00`으로 딱 떨어지는 행이 다수 발견돼 원인을 확인했다.

화면 → API DTO → 리포지토리 SQL → 원본 테이블 순으로 내려가며 확인한 결과, 어느 단계에도 값을 키우는 계산이 없었다. 원본 통계 테이블에 `86400`이 그대로 들어있는 상태였다.

이상 행의 날짜가 전부 토·일이라는 패턴을 발견해 쿼리로 검증했고, **비근무일에 미해제된 이석 상태가 종일로 마감되는** 통계 배치 이슈로 정리해 담당자에게 이관했다. 화면·API 코드는 수정하지 않았다.

## 이슈 / 특이사항

**같은 버그에 대한 중복 수정은 원인 지점을 고친 쪽을 남긴다.** 오늘 정리한 케이스가 전형적이었다. 증상을 우회하는 코드는 당장 동작하더라도, 원인이 고쳐진 뒤에는 이득 없이 로직 경로만 둘로 갈라놓는다. 특히 정렬처럼 "상태의 단일 소스"가 중요한 영역에서는 우회 경로가 나중에 어긋남의 원인이 된다.

**엑셀 내보내기 경로가 두 갈래인 프로젝트라는 걸 확인했다.** 그리드 라이브러리의 내보내기 함수를 쓰는 화면은 컬럼 `dataType` 기반으로 셀 타입이 자동 지정되지만, `e.cancel = true`로 끊고 exceljs로 직접 쓰는 화면은 전부 문자열로 저장된다. 후자가 `src/pages` 아래 39개 파일이다. 서버 페이징 상태에서 전체 행을 내보내야 해서 생긴 구조라 통합은 별도 과제로 남겼다.

**"에러가 없다"가 "정상이다"는 아니다.** 오늘 다룬 두 건 모두 예외도 경고도 없이 조용히 잘못 동작하고 있었다. 정렬은 서버가 모르는 속성을 방어적으로 무시해서, 엑셀은 텍스트도 유효한 셀 값이라서 그랬다. 이런 유형은 콘솔이 아니라 **실제로 나간 요청 파라미터**와 **실제로 저장된 파일**을 봐야 잡힌다.
