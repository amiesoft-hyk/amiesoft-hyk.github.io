백엔드 마스터 테이블을 통째로 갈아끼우는 작업과, 그리드·엑셀 쪽 버그 여러 건을 처리한 하루였다.
버그 몇 건은 따로 정리할 만해서 별도 글로 뺐고, 여기서는 전체 흐름만 묶는다.
코드는 실제 업무 코드 대신 같은 문제/해결을 재구성한 예시로 대체했다.

## 오늘 한 일

### 1. 문의유형 마스터 테이블 교체 (완료)

상담 문의유형(대/중/소) 마스터가 기존 상담앱 동기화 테이블에서 **외부 배치로 적재되는 새 테이블**로 바뀌었다. 단순 컬럼명 치환이 아니라 **키 체계 자체가 달라지는** 변경이었다.

| 기존 | 신규 | 영향 |
|---|---|---|
| `ID` (bigint, PK) | **없음** | 대체키 소멸 |
| `PARENT_ID` (bigint) | 상위 코드 (varchar) | 계층 연결이 **ID → 코드값** |
| `TYPE_LEVEL` | 코드레벨번호 | 대/중/소 구분 |
| — | `SITE_ID` (NOT NULL) | 신규 축 |

- 신규 엔티티 추가 — **원본 테이블에 PK가 없어** `@IdClass`로 `(SITE_ID, 코드)` 복합키를 식별자로 지정
- 조회 DTO에서 `id`/`parentId`(Long) 제거, `parentCode`(String) 추가
- 녹취 목록 조회의 코드명 조인을 신규 테이블 기준으로 교체
- 회차 설정에 저장되던 값이 `ID`(bigint)였으므로 **`varchar`로 컬럼 타입 변경**
- 프론트 lookup을 `value-expr="id"` → 코드값 기준으로 전환, 종속 필터를 상위 코드 비교로 변경

부수적으로 프론트에 있던 **동작하지 않는 종속 필터 버그**도 같이 잡았다. 상위 선택에 따라 하위 목록을 좁히는 코드가 응답에 존재하지 않는 필드를 참조하고 있어, 상위를 고르면 하위 목록이 **항상 비어 있었다.**

```javascript
// 응답에 없는 필드를 비교 → 항상 false
dataSource.filter(item => item.parentNm === selectedValue);

// 실제 계층 키로 비교
dataSource.filter(item => item.parentCode === selectedCode);
```

ID 기반 하위호환 보정 함수도 함께 제거했다. 저장값이 곧 코드값이 되면서 변환 단계 자체가 사라졌다.

### 2. 우수 통화 등록/해제 수정 (완료)

**해제가 DB에 반영되지 않음** — 저장 API가 등록/해제 구분값을 아예 읽지 않았다.

```java
// 기존: 이미 있으면 아무것도 안 함
Optional<Highlight> existing = repository.findByCallId(dto.getCallId());
if (existing.isPresent()) {
    continue;
}

// 수정: 해제 요청이면 소프트 삭제
if (FLAG_NO.equals(dto.getBestFlag())) {
    existing.ifPresent(item -> item.setDelFlag(FLAG_YES));
    continue;
}
if (existing.isPresent()) {
    continue;
}
```

화면은 성공 응답을 받고 아이콘을 지운 뒤 "제거되었습니다" 토스트까지 띄우는데 데이터는 그대로 남아, 관리 목록에서 사라지지 않았다.

**등록 상태가 유지되지 않음** — 목록 조회 응답 DTO에 등록 여부 필드가 아예 없었다. 프론트의 `record.bestFlag === 'Y'` 판정이 항상 `undefined`와 비교되어, **새로고침하면 등록한 항목도 미등록으로 표시**됐다. 조회 쿼리에 등록 테이블을 통화 ID로 LEFT JOIN해 존재 여부를 반환하도록 했다.

```java
new CaseBuilder()
    .when(highlight.id.isNotNull()).then(FLAG_YES)
    .otherwise(FLAG_NO)
    .as("bestFlag")
...
.leftJoin(highlight)
    .on(highlight.callId.eq(record.callId)
        .and(highlight.delFlag.eq(FLAG_NO)))
```

### 3. 관리 화면 조회 조건·필터 개선 (완료)

- 조회 조건에 **통화시간대(timeRange)** 추가. 기본값을 `00:00~23:59`로 둬서 기존 조회 결과는 그대로 유지
- 검색 시각(`HH:mm`)을 저장 형식(`HHmmss`)으로 변환해 전달. 시작은 `+00초`, 종료는 `+59초`로 채워 경계값 누락 방지
- 통화시작/종료시간 컬럼에 필터 활성화. 표시값과 필터값이 달라 `calculateDisplayCellValue` → `calculateCellValue`로 바꿔 **표시·필터·정렬 기준을 일치**시킴
- 값이 한 종류뿐인 구분 컬럼은 필터 제거
- 조회 범위가 등록자가 아닌 상담사 소속 기준이라는 점을 헤더 툴팁으로 안내

### 4. 그리드 서버 정렬 중복 수정 정리 (완료)

부서 컬럼의 서버 정렬이 먹지 않던 문제를 **서로 다른 층위에서 각각** 고쳐, 같은 목적의 코드가 겹쳐 있는 상태였다.

- **A안** — `loadOptions.sort`를 통째로 무시하고, 그리드 인스턴스에서 컬럼 상태를 읽어 정렬 파라미터를 직접 조립
- **B안** — 원인 지점을 수정. 컬럼 전처리에서 `calculateSortValue = dataField`를 명시해 표시값 함수가 정렬 selector로 잡히는 것을 차단

원인을 고치는 B안을 정본으로 남기고 A안을 걷어냈다. A안은 화면이 직접 지정한 `calculateSortValue`를 무시하고 항상 `dataField`만 쓰기 때문에, 표시 컬럼과 정렬 필드를 다르게 두려는 의도를 봉쇄한다. `dataField` 없는 계산 컬럼은 정렬이 통째로 사라지기도 한다.

부수적으로 화면 여섯 곳에 흩어져 있던 부서 3컬럼(`센터`/`팀`/`섹션`)의 `calculateSortValue` 하드코딩도 제거했다. 공통 전처리가 동일한 값을 자동으로 넣어주므로 중복이었다. 반면 lookup 코드 컬럼과 다중헤더 계산 컬럼의 지정은 공통 조건에 걸리지 않아 그대로 뒀다.

### 5. 엑셀 다운로드 시간 컬럼 표시형식 수정 (완료)

내려받은 엑셀에서 시간 컬럼이 표시형식 '일반'의 텍스트로 저장돼 `SUM()`이 동작하지 않던 문제.

- 초 단위로 환산해 86400으로 나눈 **숫자 시간값**으로 저장하고 `numFmt`를 지정하도록 수정
- 시스템 시간 서식 대신 사용자 지정 서식 `[h]:mm:ss`를 적용했다. 대괄호가 없으면 24시간에서 순환해 `24:00:00`이 `00:00:00`으로 보인다
- 별도로 만들어뒀던 유틸 파일을 없애고 기존 엑셀 공통 유틸로 통합. 사용처 네 곳의 import 경로를 함께 정리했다
- XLSX 왕복 테스트로 서식이 파일에 실제로 보존되는지 확인 (16개 통과)

### 7. 이상 집계 데이터 원인 추적 (이관)

리포트의 시간 합계가 `24:00:00`으로 딱 떨어지는 행이 다수 발견돼 원인을 확인했다.

화면 → API DTO → 리포지토리 SQL → 원본 테이블 순으로 내려가며 확인한 결과, 어느 단계에도 값을 키우는 계산이 없었다. 원본 통계 테이블에 `86400`이 그대로 들어있는 상태였다.

이상 행의 날짜가 전부 토·일이라는 패턴을 발견해 쿼리로 검증했고, **비근무일에 미해제된 이석 상태가 종일로 마감되는** 통계 배치 이슈로 정리해 담당자에게 이관했다. 화면·API 코드는 수정하지 않았다.

## 이슈 / 특이사항

**신규 테이블 조회 권한 누락** — 엔티티·쿼리를 다 맞췄는데 조회에서 실패했다.

```
SELECT command denied to user 'APP_USER'@'10.x.x.x' for table `cc_schema`.`new_code_table`
```

`Table doesn't exist`가 아니라 `command denied`였다는 점이 단서였다. 스키마 치환도 테이블 인식도 정상이고 **계정 권한만 없는 상태**였다. 권한을 확인하려다 한 번 더 걸렸다.

```
SQL Error [1141]: There is no such grant defined for user 'APP_USER' on host '10.x.x.x'
```

**에러 메시지의 호스트는 접속해 온 클라이언트 IP이지 계정에 등록된 호스트 패턴이 아니다.** 실제 계정은 `'APP_USER'@'%'` 형태였다. `mysql.user`에서 실제 host 패턴을 찾아 그 값으로 `GRANT`해야 한다.

**엑셀 내보내기 경로가 두 갈래인 프로젝트라는 걸 확인했다.** 그리드 라이브러리의 내보내기 함수를 쓰는 화면은 컬럼 `dataType` 기반으로 셀 타입이 자동 지정되지만, `e.cancel = true`로 끊고 exceljs로 직접 쓰는 화면은 전부 문자열로 저장된다. 후자가 `src/pages` 아래 39개 파일이다. 서버 페이징 상태에서 전체 행을 내보내야 해서 생긴 구조라 통합은 별도 과제로 남겼다.

**같은 버그에 대한 중복 수정은 원인 지점을 고친 쪽을 남긴다.** 증상을 우회하는 코드는 당장 동작하더라도, 원인이 고쳐진 뒤에는 이득 없이 로직 경로만 둘로 갈라놓는다. 특히 정렬처럼 "상태의 단일 소스"가 중요한 영역에서는 우회 경로가 나중에 어긋남의 원인이 된다.

**조회 화면이 비어 보이던 두 가지 함정** — 데이터 검증에 시간을 꽤 썼는데 결국 코드 문제가 아니었다.

- 화면 기본 조회월이 이번 달인데 테스트 데이터를 **지난달에 넣었다**
- 기존 데이터가 한 조직에 몰려 있어, 조직 컬럼으로 정렬해도 값이 전부 같아 **순서 변화가 눈에 보이지 않았다**

두 번째는 "정렬이 아직 안 고쳐졌다"는 오진으로 이어졌다. 이미 고쳐진 상태였는데 데이터 때문에 확인이 안 됐던 것이다. **컬럼 값의 분포부터 확인했으면** 훨씬 빨랐다.

**"에러가 없다"가 "정상이다"는 아니다.** 오늘 다룬 상당수가 예외도 경고도 없이 조용히 잘못 동작하고 있었다. 정렬은 서버가 모르는 속성을 방어적으로 무시해서, 엑셀은 텍스트도 유효한 셀 값이라서, 우수 통화 해제는 API가 성공 응답을 돌려줘서 그랬다. 이런 유형은 콘솔이 아니라 **실제로 나간 요청 파라미터**와 **실제로 저장된 데이터**를 봐야 잡힌다.

**부서 경로를 고정 인덱스로 파싱하는 코드** — 조회 범위를 정할 때 부서 경로 배열의 두 번째 요소를 무조건 "중간 부서"로 간주하는 로직을 발견했다. 조직 트리 깊이가 균일하다는 전제에 의존하므로, 조직 개편으로 깊이가 달라지면 **같은 코드가 팀을 가리킬 수도, 회사 전체를 가리킬 수도 있다.** 오류 없이 조회 범위만 조용히 달라지는 유형이라 별도로 기록해 뒀다. 이번 범위에서는 손대지 않았다.
