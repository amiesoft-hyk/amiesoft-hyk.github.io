## 오늘 한 일

### 1. 조회 안내 툴팁을 그리드 헤더에서 검색영역 상단으로 이동 (완료)

통화 이력 조회 화면의 안내 툴팁이 그리드 `No` 컬럼 헤더에 붙어 있어 눈에 잘 띄지 않았다. 리포트 화면에서 쓰던 "검색영역 좌측 정보 아이콘 + 제목 있는 팝오버" 형태로 옮겼다.

- 안내 아이콘 + 툴팁 공통 컴포넌트를 신설하고, 검색 필터 컴포넌트에 `prepend` 슬롯을 추가해 검색행 맨 앞에 배치
- 툴팁 아이콘 자리를 확보하려고 늘려뒀던 `No` 컬럼 폭을 원복
- 안내 문구를 한 줄로 축약 (조회 기준만 남김)

공통 컴포넌트를 새로 만든 부분은 되짚어볼 여지가 있었다. 리포트 쪽에 거의 동일한 컴포넌트가 이미 있었는데, 도메인 경로가 다르다는 이유로 신설했더니 결국 CSS가 중복됐다. 지금은 그대로 뒀고, 통합한다면 기존 것을 공용으로 승격시키고 리포트 쪽이 얇은 래퍼가 되는 방향이 맞다.

### 2. 그리드 헤더필터 "(필드 값 없음)" 미동작 수정 (완료)

헤더필터에서 "(필드 값 없음)"을 체크해도 필터가 걸리지 않고 전체가 조회되던 문제. 프론트는 정상이었고 원인은 전부 서버였다.

두 가지 유형으로 나뉘었다.

- **검색 DTO가 공통 부모 클래스를 상속하지 않은 경우** — 공백 필드 파라미터를 담을 곳 자체가 없어 전체 컬럼이 미동작. 4개 DTO가 해당했고, 화면 기준으로 8개 화면 51개 컬럼
- **상속은 했지만 필터 헬퍼가 검색 조건 객체를 안 받는 경우** — 공백 여부를 확인할 방법이 없어 조건이 통째로 사라짐

수정 대상은 이력 조회, 근태 관리 계열 5화면, 근무 편성 2화면, 개인 리포트 등 9개 화면이었다.

상세는 별도 글로 정리했다.

### 3. 제외(체크 해제) 시 빈 값 행이 사라지던 문제 함께 해소 (완료)

`NOT IN`이 SQL 3값 논리 때문에 `NULL` 행을 함께 떨어뜨리고 있었다. 공백 처리를 넣으면서 `NOT IN (...) OR IS NULL` 형태로 바꿔 함께 정리했다. 이것도 별도 글로 정리.

### 4. 구현 방식 전환 — 리플렉션 엔진 도입 → 제거 → 재도입 (완료)

오늘 가장 많이 왔다 갔다 한 부분이다.

처음엔 "필드 → 표현식 매핑 한 곳 + 리플렉션으로 게터를 찾아 일괄 적용"하는 공통 엔진을 만들었다. 컬럼별 나열이 사라지고 코드도 줄었지만, 되짚어보니 **엔진 209줄을 추가해서 3개 파일만 쓰고 있었다.** 같은 목적의 기존 유틸은 이미 20개 파일이 쓰고 있었고, 그 유틸에 인자 두 개만 넘기면 되는 일이었다.

그래서 커밋을 되돌리고 기존 방식으로 통일했다가, 다시 리플렉션 방식으로 돌아왔다. 대신 원래 지적됐던 약점을 보완했다.

```java
// 맵에 선언했는데 대응 게터가 없으면 조건이 조용히 사라진다.
// 리플렉션이라 컴파일 시점에 안 잡히므로 로그로 드러낸다.
private static void warnIfGetterMissing(GridSearch search, String field) {
    if (findGetter(search.getClass(), field + "List") != null
        || findGetter(search.getClass(), field + "ExcludeList") != null) {
        return;
    }
    log.warn("헤더필터 조건이 적용되지 않습니다. 필드명이 화면 dataField 와 같은지 확인하세요: {}", field);
}
```

`{field}List`와 `{field}ExcludeList`가 **둘 다 없을 때만** 경고하므로, `From`/`To`처럼 원래 없는 게 정상인 경우에는 로그가 남지 않는다.

## 이슈 / 특이사항

### lookup 컬럼의 표시 기준과 필터 기준이 어긋남 (미해결)

수정 후에도 특정 화면에서 "(필드 값 없음)"이 안 먹는다는 얘기가 나왔다. SQL을 확인하니 조건은 정확히 들어가 있었다.

원인은 **화면의 `-`가 "빈 값"을 뜻하지 않는다**는 것이었다. 공통 그리드가 lookup 목록에 없는 코드값도 `-`로 표시하고 있어서, 눈에는 비어 보이지만 DB에는 값이 있는 행이었다. 게다가 DevExtreme은 lookup 컬럼의 헤더필터 항목을 lookup 목록 기준으로 만들기 때문에, 그런 행은 어떤 항목으로도 선택할 수 없는 사각지대에 있었다.

같은 파일의 정렬 로직은 이미 "코드 목록에 없으면 빈 값"으로 취급하고 있어서, **정렬은 화면 기준·필터는 DB 원본 기준**이라는 불일치가 있었다. 필터도 화면 기준으로 맞추는 방향으로 정리할 예정. 이것도 별도 글로 남겼다.

### 자동 감사 스크립트의 한계

전체 화면을 대상으로 "어느 컬럼이 공백 처리를 안 하는가"를 스크립트로 뽑으려 했는데 오탐이 많았다. 파일마다 헬퍼 인자 규약이 제각각이었기 때문이다.

```java
addTextCondition(predicates, column, param, keyword, inc, exc, search, field);     // field 가 마지막
addExactCondition(predicates, column, param, inc, exc, search, "flagCd", empty);   // field 가 중간
applyTextCondition(condition, path, req.getName(), ...);                           // 변수명이 search 가 아님
```

"마지막 문자열 리터럴이 필드명"이라는 가정이 깨져서, 실제로는 정상인 파일이 미지원으로 나왔다. 결국 파일을 직접 열어 확인하는 쪽이 빨랐다. **정적 분석으로 코딩 관행을 추론하려면 관행이 먼저 통일되어 있어야 한다**는 걸 확인한 셈이다.

### 프로젝트 테스트 실행이 막혀 있음

빌드 스크립트에 테스트 전체를 제외하는 설정이 있어서 JUnit을 돌릴 수 없었다.

```groovy
tasks.named('test') {
    useJUnitPlatform()
    exclude "**/*"
}
```

이번에는 `main` 메서드로 실행 가능한 검증 클래스를 만들고, Gradle init script로 임시 `JavaExec` 태스크를 추가해 확인했다. 프로젝트 빌드 파일은 건드리지 않았다.
