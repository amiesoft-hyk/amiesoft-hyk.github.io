## 문제 상황

하나의 메뉴 기능을 제공하는 프런트엔드에 서로 다른 URL의 페이지 두 개가 존재했고, 두 페이지가 같은 조회 API를 호출하고 있었다. 정식 메뉴에는 첫 번째 URL만 등록되어 있었지만, 소스에는 두 번째 URL과 별도 페이지 컴포넌트도 남아 있었다.

겉으로 보면 두 화면이 의도적으로 같은 API를 공유하는 것처럼 보인다. 하지만 메뉴 등록, 라우트 생성 시점, 화면 변경 이력을 함께 확인하니 기능 이전 과정에서 이전 구현이 정리되지 않은 사례였다.

## 원인

### 새 화면을 별도 라우트로 먼저 개발했다

커밋 이력을 따라가면 새 조회 기능은 기존 메뉴 화면을 바로 수정하지 않고, 별도의 페이지와 라우트로 먼저 추가되었다. 이 화면은 로그인 사용자를 기준으로 이수 내역을 조회하는 전용 API를 사용했다.

```js
const routes = [
  {
    path: '/account/training-summary',
    component: () => import('./training-summary-page.vue'),
  },
];

await callApi({
  action: 'GET_MY_TRAINING_SUMMARY',
  data: searchCondition,
});
```

### 이후 기존 메뉴 화면을 같은 기능으로 교체했다

후속 커밋에서는 기존 메뉴 URL을 유지한 채 화면 내용을 새 이수 현황 UI로 변경했다. 이 과정에서 기존 화면이 사용하던 교육 진행 조회 API가 새 이수 현황 API로 교체됐다.

```js
// 변경 전: 교육 참여, 자료, 피드백 등 진행 정보 조회
await callApi({ action: 'GET_MY_TRAINING_PROGRESS' });

// 변경 후: 개인별 이수 시간 조회
await callApi({ action: 'GET_MY_TRAINING_SUMMARY' });
```

그러나 선행 개발에 사용한 별도 페이지와 라우트는 삭제하지 않았다. 결과적으로 서로 다른 URL 두 개가 같은 화면 목적과 같은 API를 갖게 되었다.

### 라우트와 메뉴 메타데이터의 생명주기가 달랐다

프런트엔드 라우터에는 두 URL이 모두 존재했지만, 권한 검사에 사용되는 메뉴 메타데이터에는 기존 URL만 등록되어 있었다. 따라서 추가 라우트는 소스상 접근 가능해 보여도 실제 인증 환경에서는 메뉴 권한 검사에 막힐 수 있었다.

이 차이는 단순한 중복 코드를 넘어 다음 문제를 만든다.

- 어느 URL이 정식 진입점인지 알기 어렵다.
- 한 화면만 수정하면 두 화면의 동작이 달라진다.
- 사용되지 않는 API와 권한 설정이 계속 유지된다.
- 나중에 라우트를 정리할 때 삭제 범위를 판단하기 어렵다.

## 해결 방법

### 커밋 전체가 아니라 기능 경계를 기준으로 복원한다

문제가 생긴 커밋에는 대상 화면 외에도 공통 그리드와 Excel 유틸리티 변경이 함께 포함되어 있었다. 따라서 커밋 전체를 `revert`하면 다른 화면에서 사용 중인 개선까지 되돌릴 수 있다.

안전한 복원 범위는 다음과 같이 잡았다.

1. 정식 메뉴의 페이지 컴포넌트만 기능 변경 이전 버전으로 복원한다.
2. 선행 개발용으로 추가된 중복 페이지를 삭제한다.
3. 라우터 파일에서는 중복 라우트 블록만 제거한다.
4. 다른 화면도 사용하는 공통 컴포넌트와 Excel 유틸리티는 유지한다.
5. 백엔드의 전용 엔드포인트와 권한 메타데이터는 참조가 사라졌는지 확인한 뒤 정리한다.

```text
정식 메뉴 URL
  └─ 기존 진행 정보 화면과 API로 복원

임시 중복 URL
  ├─ 페이지 컴포넌트 삭제
  └─ 라우트 등록 삭제

공통 모듈
  └─ 다른 사용처가 있으므로 유지
```

### 기준 커밋과 현재 파일을 직접 비교한다

단순히 커밋 메시지만 보고 되돌리지 않고, 기준 커밋과 현재 상태 사이에서 대상 경로에 어떤 파일이 추가·수정되었는지 확인한다.

```bash
git diff --name-status <baseline>..<change> -- path/to/feature
git log --follow -- path/to/page.vue
git blame -L <start>,<end> -- path/to/page.vue
```

이렇게 하면 새로 생긴 파일, 기존 파일의 대규모 교체, 이후 추가된 후속 수정까지 분리할 수 있다.

### 프런트엔드와 백엔드 참조를 함께 검사한다

화면만 제거하고 전용 API를 남기거나, 반대로 API를 먼저 제거하면 불완전한 롤백이 된다. 액션명과 엔드포인트를 전체 저장소에서 검색해 잔여 사용처를 확인해야 한다.

```bash
rg "GET_MY_TRAINING_SUMMARY|/account/training-summary" .
```

검증 항목은 다음과 같다.

- 정식 URL이 기존 API를 호출하는가?
- 중복 URL이 더 이상 라우터에 등록되지 않는가?
- 제거 대상 API 액션의 사용처가 남아 있지 않은가?
- 메뉴명과 실제 화면 기능이 다시 일치하는가?
- 작업 전에 존재한 다른 로컬 변경이 보존됐는가?

## 결과

두 화면이 같은 API를 사용한 것은 의도적인 공용화가 아니라, 새 기능을 별도 라우트에서 먼저 개발한 뒤 기존 메뉴 화면으로 이식하면서 선행 구현을 제거하지 않았기 때문이었다.

이 사례에서 중요한 점은 특정 커밋을 통째로 되돌리는 것이 항상 올바른 롤백은 아니라는 것이다. 하나의 커밋에 공통 모듈 변경과 화면 기능 변경이 섞여 있다면, 기준 시점의 파일을 확인하고 기능 경계별로 복원해야 후속 개선과 다른 화면을 보호할 수 있다.

라우트 중복 문제를 조사할 때는 라우터 정의만 보지 말고 페이지의 API 호출, 메뉴 권한 메타데이터, 백엔드 엔드포인트, 커밋 이력을 한 흐름으로 추적하는 것이 가장 확실하다.
